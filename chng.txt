CRQ000000807543 – Change Request Detailed Documentation

Overview
This document provides a comprehensive and detailed explanation of the change request involving the rebuild and redeployment of all Storefront services using updated COSRT base images to ensure certificate chain continuity before the November 30 expiration. The change is strictly related to infrastructure compliance, without introducing any code changes or functional modifications to the services.

Background
GEICO's intermediate certificates are set to expire on November 30. Multiple internal platforms, including Storefront, rely on these certificates for secure service communication. The Storefront ecosystem consists of several microservices, including the Storefront API, Storefront External Service, Storefront UI, and Storefront Admin UI. All of these require updated base images that include the new certificate chain published by COSRT.

Failure to rebuild and redeploy these applications before the certificate expiry date poses a risk of service disruptions across internal workflows, device ordering pipelines, Slack approvals, Remedy integrations, and general API access. This CR has been initiated to proactively rebuild and redeploy the services using the latest COSRT base images, ensuring the updated certificate chain is included and services remain stable and compliant.

Scope of Change
The scope covers all core Storefront microservices:

1. Storefront API
2. Storefront External Service
3. Storefront UI
4. Storefront Admin UI

The change does not alter application logic, business rules, or user interface components. It is strictly a container platform refresh to incorporate updated certificate chain data from COSRT-published images. All services will be rebuilt, redeployed, verified, and promoted through standard environment progression (DEV → UAT → PROD).

Business Justification
This CR is required to ensure the continuity of Storefront operations following the expiration of the current GEICO intermediate certificate. Without updating the base images and redeploying the affected microservices, certificate validation failures may occur, potentially interrupting critical workflows such as device ordering processes, automated notifications, Remedy group-tag validation, and cross-platform integrations.

Updating the COSRT base images and redeploying ensures:

* Certificate compliance before the deadline
* Elimination of potential service outages caused by expired certificates
* Alignment with platform security guidelines and operational best practices
* Maintaining uninterrupted availability across all Storefront applications and services

Impact Analysis

1. Functional Impact:
   No functional impact is expected. There are no code changes being introduced, and the business logic, workflows, integrations, and UI components remain unchanged.

2. Application Availability:
   During the redeployment process, ArgoCD will manage rollout through controlled strategies. Traffic will only be routed to new pods once they are verified as healthy. If new pods fail health checks, ArgoCD will not proceed, preventing downtime.

3. User Impact:
   There is no impact to internal or external users. All interfaces and workflows will continue functioning normally.

4. Integration Impact:
   Slack approvals, Remedy workflows, group-tag population, device ordering flows, and data synchronization will remain fully operational.

5. Monitoring:
   All logs and application performance data will be monitored continuously through Grafana (Titan) dashboards. Any anomalies will be immediately visible and triaged.

Implementation Plan
The implementation will follow a structured and controlled multi-step approach:

1. Preparation Phase:

* Confirm availability of updated COSRT base images
* Validate that all required certificate updates are included in the base image
* Ensure ArgoCD pipelines are aligned and ready for deployment

2. Image Rebuild:

* Build updated Docker images for:
  a. Storefront API
  b. Storefront External Service
  c. Storefront UI
  d. Storefront Admin UI
* Verify that each image contains the updated certificate chain

3. Deployment Process:

* Deploy updated images to the DEV environment
* Validate successful deployment including:

  * Pod readiness
  * Endpoint accessibility
  * UI rendering
  * Internal API communication
  * Log verification via Grafana
* Promote changes to UAT
* Perform the same validations
* Schedule and execute PROD deployment using ArgoCD

4. Validation:

* Application logs will be reviewed for certificate-related errors
* Network and TLS handshake validation will be performed
* Cross-service communication will be tested for certificate acceptance

5. Completion:

* Document deployment results
* Notify dependent teams of successful rollout

Back-Out Plan
The rollback strategy leverages ArgoCD's automated monitoring and rollback capabilities.

1. If new pods fail readiness checks, ArgoCD will not route traffic to them, preventing runtime issues.
2. Manual rollback can be triggered at any time through the ArgoCD interface to restore the previous stable version.
3. Since no schema or configuration changes are introduced, rollback is instantaneous and risk-free.
4. Backup contact for emergency recovery: Michael Gardner.

No persistent data or system state changes are introduced by this CR, ensuring a safe and clean back-out path.

Conclusion
